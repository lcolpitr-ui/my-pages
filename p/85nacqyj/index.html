🧠 超大项目上下文不够？

三种完整解决方案，让你用 Claude Code / Cursor / 任何 AI 编程工具，完整交付超大型项目

方案一 · 项目拆分法 方案二 · 渐进式上下文管理 方案三 · 多 Agent 流水线

⚠️ 核心问题

当你试图用 AI 编程工具完成一个大型项目时，会遇到以下瓶颈：

  • 上下文窗口有限 — Claude 200K tokens、GPT-4 128K tokens，放不下完整项目
  • 单次对话无法持续 — 长对话会丢失早期指令和代码细节
  • 文件间依赖复杂 — 修改 A 文件可能破坏 B、C、D 文件
  • AI 会"遗忘" — 超过一定长度后，AI 开始重复生成或遗漏关键逻辑

📑 目录

  1. 方案一：项目拆分法（Monorepo + 子模块独立迭代）
  2. 方案二：渐进式上下文管理（CLAUDE.md + Memory + 规则系统）
  3. 方案三：多 Agent 流水线（Orchestrator → Worker → Reviewer）
  4. 三种方案对比表
  5. 总结与推荐组合
1

项目拆分法

Monorepo + 子模块独立迭代

核心思路：把一个"装不下"的大项目，拆成多个"装得下"的小模块。每个模块独立开发、独立测试，最后组装。

1 分析项目结构，识别拆分边界

首先让 AI 帮你分析整个项目的架构，找到天然的拆分边界：

Claude Code 对话 # 第一步：让 AI 分析项目，输出模块拆分建议 请分析这个项目的完整结构，帮我做模块拆分规划： 1. 列出所有顶层目录和它们的职责 2. 识别模块之间的依赖关系 3. 给出建议的拆分方案，每个模块不超过 15,000 行 4. 输出一个 dependency graph（依赖图） # AI 会输出类似: # - auth/ → 独立模块，无外部依赖 # - payments/ → 依赖 auth（接口层） # - dashboard/ → 依赖 auth + payments（接口层） # - shared/ → 工具库，被所有模块引用

2 创建 Monorepo 项目结构

用标准的 Monorepo 结构组织拆分后的模块：

目录结构 my-big-project/ ├── CLAUDE.md ← 全局项目说明（每次对话自动加载） ├── package.json ← 工作区根配置 ├── turbo.json ← Turborepo 构建编排 │ ├── packages/ │ ├── shared/ ← 公共工具库 (~3,000 行) │ │ ├── src/ │ │ ├── tests/ │ │ ├── CLAUDE.md ← 模块专属上下文 │ │ └── package.json │ │ │ ├── auth/ ← 认证模块 (~8,000 行) │ │ ├── src/ │ │ ├── tests/ │ │ ├── CLAUDE.md │ │ └── package.json │ │ │ ├── payments/ ← 支付模块 (~12,000 行) │ │ ├── src/ │ │ ├── tests/ │ │ ├── CLAUDE.md │ │ └── package.json │ │ │ └── dashboard/ ← 仪表盘 (~15,000 行) │ ├── src/ │ ├── tests/ │ ├── CLAUDE.md │ └── package.json │ └── apps/ └── web/ ← 主应用入口，组装所有模块 ├── src/ └── package.json
package.json (根目录) { "name": "my-big-project", "private": true, "workspaces": [ "packages/*", "apps/*" ], "scripts": { "dev": "turbo dev", "build": "turbo build", "test": "turbo test", "lint": "turbo lint" }, "devDependencies": { "turbo": "^2.0.0" } }

3 为每个模块编写 CLAUDE.md

每个模块目录下放一个 CLAUDE.md，记录该模块的关键上下文。当 AI 在该目录下工作时，会自动读取：

packages/payments/CLAUDE.md # Payments 模块 ## 职责 处理所有支付相关逻辑：创建支付、退款、Webhook 回调。 ## 依赖 - @myproject/shared — 工具函数 - @myproject/auth — 仅使用其 IUser 接口和 verifyToken() ## 核心文件 - `src/stripe.ts` — Stripe SDK 封装 - `src/webhook.ts` — Webhook 签名验证 + 事件分发 - `src/refund.ts` — 退款逻辑 - `src/types.ts` — 支付相关类型定义 ## 接口约定 // 供其他模块调用的公开 API export function createPayment(userId: string, amount: number): Promise<Payment> export function refundPayment(paymentId: string): Promise<Refund> ## 测试 - 单元测试: `tests/unit/` - 集成测试: `tests/integration/` (需要 Stripe test key) - 运行: `pnpm test --filter @myproject/payments` ## 注意事项 - 所有金额用 整数（分） 存储，不要用浮点数 - Webhook 必须验证签名，防止伪造 - 退款有 30 天限制

💡 关键技巧

每个模块完成后，让 AI 更新该模块的 CLAUDE.md，记录最终的 API 接口、架构决策和已知问题。这样下一个模块的对话可以参考已有的接口，而不是重新理解整个代码。

5 集成测试与组装

所有模块完成后，开一轮新对话做集成：

集成对话 cd apps/web claude # 提示词: 请帮我完成主应用的集成工作： 1. 读取 packages/*/CLAUDE.md 了解所有模块的 API 2. 在 apps/web/src 中创建路由，串联 auth → payments → dashboard 3. 配置统一的错误处理和日志 4. 编写 E2E 测试覆盖核心用户流程 5. 运行 `turbo test` 确保所有模块测试通过
2

渐进式上下文管理

CLAUDE.md + Memory + 规则系统

核心思路：不拆项目结构，而是通过精心设计的上下文文件系统，让 AI 每次只加载"当前需要的"上下文，同时保留全局记忆。

🏗️ 上下文层次架构
  ┌─────────────────────────────────────────────────────────────────┐
  │                        AI 对话上下文                             │
  │                                                                 │
  │  ┌───────────────────────────────────────────────────────────┐  │
  │  │ L1: 全局规则 (每次自动加载，~2K tokens)                     │  │
  │  │ ~/.claude/settings.json + ~/.claude/rules/                │  │
  │  │ → 编码风格、安全规范、Git 流程                               │  │
  │  └───────────────────────────────────────────────────────────┘  │
  │                              ▼                                  │
  │  ┌───────────────────────────────────────────────────────────┐  │
  │  │ L2: 项目说明 (每次自动加载，~3K tokens)                     │  │
  │  │ ./CLAUDE.md                                               │  │
  │  │ → 项目概述、架构、技术栈、核心约定                           │  │
  │  └───────────────────────────────────────────────────────────┘  │
  │                              ▼                                  │
  │  ┌───────────────────────────────────────────────────────────┐  │
  │  │ L3: 模块上下文 (按需加载，~5K tokens)                      │  │
  │  │ ./docs/modules/{module-name}.md                           │  │
  │  │ → 由 AI 读取或用户在对话中引用                               │  │
  │  └───────────────────────────────────────────────────────────┘  │
  │                              ▼                                  │
  │  ┌───────────────────────────────────────────────────────────┐  │
  │  │ L4: 任务上下文 (临时，本次对话有效)                         │  │
  │  │ 当前正在编辑的文件 + 相关依赖                                │  │
  │  │ → AI 通过 Read/Grep 工具按需加载                            │  │
  │  └───────────────────────────────────────────────────────────┘  │
  │                              ▼                                  │
  │  ┌───────────────────────────────────────────────────────────┐  │
  │  │ L5: 记忆系统 (跨对话持久化)                                │  │
  │  │ ~/.claude/projects/{project}/memory/*.md                  │  │
  │  │ → 架构决策、已修复的 bug、重要发现                           │  │
  │  └───────────────────────────────────────────────────────────┘  │
  └─────────────────────────────────────────────────────────────────┘

1 编写项目级 CLAUDE.md

这是最重要的文件。AI 每次启动对话都会自动读取它。必须精炼，控制在 3000 tokens 以内：

./CLAUDE.md (项目根目录) # MyProject — 全栈 SaaS 平台 ## 技术栈 - Frontend: React 18 + TypeScript + Vite + TailwindCSS - Backend: Node.js + Express + Prisma + PostgreSQL - Infra: Docker + GitHub Actions + AWS ECS ## 项目结构 ├── src/ │ ├── client/ # React 前端 │ ├── server/ # Express 后端 │ ├── shared/ # 前后端共享类型 │ └── prisma/ # 数据库 schema ├── tests/ ├── docs/ # 模块文档 (AI 按需读取) └── scripts/ ## 核心约定 1. 所有 API 返回统一格式: { success, data, error, meta } 2. 数据库操作只通过 Prisma，禁止裸 SQL 3. 前端状态管理用 Zustand，不要用 Redux 4. 错误处理: 用 AppError 类，不用 throw new Error() 5. 认证: JWT + refresh token，access token 15 分钟过期 ## 常用命令 - `pnpm dev` — 同时启动前后端 - `pnpm test` — 运行全部测试 - `pnpm db:migrate` — 运行数据库迁移 - `pnpm lint` — ESLint + Prettier 检查 ## 模块文档 详细的模块说明在 docs/ 目录下，需要时请读取: - docs/auth.md — 认证系统 - docs/payments.md — 支付系统 - docs/dashboard.md — 仪表盘 - docs/api-design.md — API 设计规范

2 创建模块文档（按需加载）

每个复杂模块写一个详细的 Markdown 文档，放在 docs/ 目录：

docs/payments.md # 支付系统模块文档 ## 架构 使用 Stripe 作为支付网关，支持一次性支付和订阅。 ## 核心文件 | 文件 | 职责 | 行数 | |------|------|------| | server/src/payments/stripe.ts | Stripe 客户端初始化 | 45 | | server/src/payments/checkout.ts | 创建 checkout session | 120 | | server/src/payments/webhook.ts | 处理 Stripe webhook | 200 | | server/src/payments/refund.ts | 退款逻辑 | 80 | | server/src/payments/subscription.ts | 订阅管理 | 150 | | shared/src/types/payment.ts | 类型定义 | 60 | ## 数据库表 ```sql Payment: id, userId, stripePaymentId, amount, currency, status, createdAt Subscription: id, userId, stripeSubId, plan, status, currentPeriodEnd Refund: id, paymentId, amount, reason, status, createdAt ``` ## API 端点 - POST /api/payments/checkout — 创建支付 - POST /api/payments/webhook — Stripe 回调 (无需 auth) - POST /api/payments/:id/refund — 退款 - GET /api/subscriptions/:userId — 查询订阅 ## 依赖关系 - 依赖 auth 模块: 使用 requireAuth() 中间件 - 依赖 shared: 使用 AppError, ApiResponse 类型 - 被 dashboard 模块引用: 展示支付历史 ## 已知问题 - [ ] Stripe webhook 在本地开发需要用 stripe cli - [x] 退款超过 30 天的限制已处理 - [x] 货币转换逻辑已迁移到 shared/currency.ts
📖 使用方式

在对话中告诉 AI："请先读取 docs/payments.md，然后帮我修复 webhook 签名验证的 bug"。AI 会先加载文档获得完整上下文，再开始工作。

让 AI 自动保存记忆 # 在对话结束前，让 AI 记住关键发现: 这次对话我们修复了 webhook 签名验证的问题。 请把这个发现保存到 memory 中，包括： 1. 问题描述 2. 根因 (raw body 解析顺序) 3. 修复方法 4. 如何避免类似问题 # AI 会创建/更新 memory 文件: # ~/.claude/projects/{hash}/memory/stripe-webhook-fix.md # 下次新对话时，AI 会自动读取 MEMORY.md 索引 # 并根据当前任务按需加载相关记忆文件

多 Agent 流水线

Orchestrator → Worker → Reviewer

核心思路：用一个主控 Agent 拆分任务，分配给多个工作 Agent 并行执行，最后由审查 Agent 验证。每个 Agent 只处理自己那部分上下文。

  # 关键: 通过 phase 控制执行顺序
  phase('Database')  → 先完成
  phase('Backend')   → 读取 DB 输出
  phase('Frontend')  → 读取 API 输出
⚠️ 并行 vs 串行的选择

可并行：当两个 Agent 没有文件级依赖时（如前端 UI 设计 + 后端数据库设计）

必须串行：当 Agent B 需要读取 Agent A 生成的代码时（如 API 需要先有数据库 schema）

在 Workflow 中用 phase() 控制执行顺序，同 phase 内的 agent 并行执行。
